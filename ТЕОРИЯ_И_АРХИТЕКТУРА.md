## 1. Событийно-ориентированная архитектура (EDA) и Брокеры сообщений

### Почему брокер сообщений вместо прямых HTTP/REST вызовов?
В ЛР №1–3 сервисы общались синхронно по HTTP (через OpenFeign / WebClient). В ЛР №4 внедрена **Событийно-ориентированная архитектура (Event-Driven Architecture, EDA)** на базе Apache Kafka.

| Критерий | Синхронный HTTP (REST) | Асинхронный брокер (Kafka) |
|---|---|---|
| **Связность (Coupling)** | **Тесная (Tight Coupling):** Сервис-отправитель должен знать сетевой адрес и контракт сервиса-получателя. | **Слабая (Loose Coupling):** Сервисы знают только о структуре события в топике. Отправитель не знает, кто и когда прочитает событие. |
| **Доступность (Availability)** | Если сервис-получатель упал, запрос завершается ошибкой (503/Timeout) либо требует сложных Circuit Breaker'ов. | **Высокая:** Если получатель временно недоступен, сообщения безопасно хранятся в Kafka. Как только получатель поднимется, он вычитает их из очереди (Offset). |
| **Производительность** | Поток отправителя блокируется в ожидании HTTP-ответа (Latency суммируется). | **Мгновенная:** Запись в Kafka занимает единицы миллисекунд (append-only log на диске). |
| **Масштабируемость** | Вызов 1 к 1 (Point-to-Point). Для 5 получателей нужно сделать 5 HTTP-запросов. | **Publish-Subscribe (1 ко многим):** Одно событие в топике могут читать независимо десятки разных консьюмеров. |
| **Пиковые нагрузки** | Всплеск трафика может уронить зависимый сервис (Throttling / OOM). | **Буферизация (Backpressure):** Kafka сглаживает пики. Консьюмер вычитывает сообщения с той скоростью, с которой способен обработать. |

## 2. Внутреннее устройство Apache Kafka и режим KRaft

### Что такое режим KRaft (Kafka Raft)?
Исторически Kafka требовала сторонний координатор **Apache ZooKeeper** для хранения метаданных кластера, выбора лидера партиций и управления конфигурацией топиков. Это усложняло администрирование, приводило к рассинхронизации данных между ZooKeeper и Kafka и ограничивало масштабируемость (миллионы партиций упирались в дерево ZooKeeper).

Начиная с версии Kafka 3.x и в нашей реализации (**Apache Kafka 3.8.0**), используется **KRaft (Kafka Raft Metadata Mode)**:
1. Метаданные кластера хранятся **внутри самой Kafka** в специальном внутреннем топике `@metadata`.
2. Консенсус между контроллерами достигается с помощью распределённого алгоритма **Raft**.
3. Ноды могут совмещать роли: `KAFKA_PROCESS_ROLES: broker,controller`.
4. Кластер объединяется единым идентификатором: `KAFKA_KRAFT_CLUSTER_ID: 4L622nShTWWkrFuMm50BAw`.
5. Переключение лидера при аварии происходит за **десятки миллисекунд** вместо секунд в ZooKeeper.

## 3. Партиционирование, Фактор репликации 3 и Отказоустойчивость

### Как устроен топик Kafka?
Топик — это логическая категория для сообщений. Физически топик делится на **партиции (Partitions)**.
- Партиция представляет собой упорядоченный, неизменяемый журнал записей (**Append-Only Commit Log**).
- Каждому сообщению в партиции присваивается монотонно возрастающий номер — **Offset** (смещение).
- **Партиция — единица параллелизма:** Несколько инстансов консьюмеров из одной **Consumer Group** могут параллельно читать разные партиции одного топика.

В нашем проекте каждый топик создан с **3 партициями**:
```bash
/opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka-1:9092 --create \
  --topic employee-events --partitions 3 --replication-factor 3
```

### Фактор репликации 3 (Replication Factor = 3)
Фактор репликации 3 означает, что каждая партиция топика физически сохраняется на **трёх независимых брокерах кластера** (`kafka-1`, `kafka-2`, `kafka-3`).

1. **Leader Replica (Лидер):** Ровно одна реплика назначается лидером. Все операции записи (`Produce`) и чтения (`Consume`) по умолчанию направляются лидеру.
2. **Follower Replicas (Фолловеры):** Остальные две реплики пассивно копируют записи лидера.
3. **ISR (In-Sync Replicas):** Множество реплик, которые полностью синхронизированы с лидером (отставание не превышает порога `replica.lag.time.max.ms`).
4. **Гарантии надёжности продюсера (`acks=all`):**
   - В `file-service` и других продюсерах настроено `acks: all` (или `-1`). Это означает, что брокер подтверждает успешную запись только тогда, когда запись закоммичена лидером и **всеми синхронными репликами (ISR)**.
   - Параметр `min.insync.replicas=2` гарантирует: даже если один из брокеров отключится, запись успешно зафиксируется на двух оставшихся. Если упадут два брокера, запись отклонится во избежание потери данных.

## 4. Чистая Архитектура (Clean Architecture / Hexagonal Architecture)

В `notification-service` и `file-service` реализована эталонная **Чистая Архитектура (Роберт Мартин / Alistair Cockburn)**:

### Слои и их обязанности:
```
[ Infrastructure: Adapters ]  --->  [ Application: Use Cases & Ports ]  --->  [ Domain: Entities ]
```

1. **Domain Layer (Ядро бизнеса):**
   - *Пакет:* `portal.<service>.domain`
   - *Элементы:* `StoredFile`, `Notification`, `NotificationType`, `FileNotFoundException`, `FileStorageException`.
   - *Характеристика:* **0 внешних зависимостей**. Никакого Spring, никаких аннотаций JPA (`@Entity`, `@Table`), никакого Jackson. Чистая Java 21 бизнес-логика.
2. **Application Layer (Сценарии использования):**
   - *Пакет:* `portal.<service>.application`
   - *Элементы:*
     - **Inbound Ports (Use Cases):** `UploadFileUseCase`, `DownloadFileUseCase`, `GetNotificationsUseCase`, `MarkNotificationReadUseCase`. Интерфейсы, описывающие действия, которые система может выполнять.
     - **Outbound Ports (SPI - Service Provider Interfaces):** `FileStoragePort`, `FileMetadataRepositoryPort`, `FileEventPort`, `NotificationRepositoryPort`. Интерфейсы к внешним системам (БД, хранилище, шина событий).
     - **Application Services:** `FileApplicationService`, `NotificationApplicationService`. Реализуют Use Cases, координируют доменные сущности и вызывают Outbound Ports. Не зависят от деталей реализации хранилищ.
3. **Infrastructure Layer (Адаптеры и Фреймворки):**
   - *Пакет:* `portal.<service>.infrastructure`
   - *Inbound Adapters (Входящие):*
     - `NotificationController`, `FileController` — REST API адаптеры (принимают HTTP, мапят DTO в доменные модели, вызывают Use Cases).
     - `NotificationKafkaConsumer` — Kafka адаптер (слушает топики, преобразует события в уведомления).
   - *Outbound Adapters (Исходящие):*
     - `LocalDiskFileStorageAdapter` — реализует `FileStoragePort` (работает с локальной файловой системой через `java.nio.file`).
     - `FileMetadataRepositoryAdapter` — реализует `FileMetadataRepositoryPort` (обёртка над Spring Data JPA).
     - `FileEventKafkaProducerAdapter` — реализует `FileEventPort` (публикует события в Kafka через `KafkaTemplate`).
     - `SecurityConfig`, `JwtService`, `JwtAuthenticationFilter` — адаптеры безопасности.

### Принцип Инверсии Зависимостей (Dependency Inversion Principle):
Бизнес-логика (`FileApplicationService`) требует сохранения файла на диск и записи метаданных в базу. Но она не обращается напрямую к диску или SQL! Она обращается к интерфейсам `FileStoragePort` и `FileMetadataRepositoryPort`. Адаптеры на слое Infrastructure реализуют эти интерфейсы. Таким образом, мы можем легко заменить локальный диск на Amazon S3 или MinIO, не изменив **ни единой строчки** в Application или Domain слоях!

## 5. Архитектура микросервиса файлов (`file-service`)

- **Порт:** `8085`
- **Маршрут через шлюз:** `/api/files/**`
- **Назначение:** Загрузка, безопасное локальное хранение и скачивание документов/вложений (больничные, заявления на отпуск, аватарки).
- **Схема работы:**
  1. Клиент отправляет `POST /api/files/upload` (`multipart/form-data`).
  2. Файл валидируется на непустоту и размер ($\le 50$ МБ).
  3. Генерируется уникальное имя на диске (UUID + расширение).
  4. Байты сохраняются в том `file_uploads` через `LocalDiskFileStorageAdapter`.
  5. Метаданные (оригинальное имя, размер, тип MIME, автор, дата) сохраняются в таблицу `file_metadata` PostgreSQL через Flyway V1.
  6. Генерируется событие `FileEventDto` (`FILE_UPLOADED`) и публикуется в топик `file-events` Kafka.
  7. Клиент получает JSON с метаданными и ссылкой на скачивание (`/api/files/{id}/download`).

## 6. Архитектура микросервиса уведомлений (`notification-service`)

- **Порт:** `8084`
- **Маршрут через шлюз:** `/api/notifications/**`
- **Назначение:** Агрегация системных и персональных оповещений, формирование ленты событий.
- **Подписка на топики Kafka:**
  - `notification-events` — прямые уведомления пользователям и ролям.
  - `attendance-events` — детекция опозданий (`LATE_ARRIVAL`) и переработок (`OVERTIME`) сотрудников, уведомление менеджеров.
  - `schedule-events` — уведомления о назначении смен (`SHIFT_ASSIGNED`) и результатах рассмотрения заявок (`REQUEST_APPROVED`, `REQUEST_REJECTED`).
  - `employee-events` — кадровые уведомления (`EMPLOYEE_CREATED`, `EMPLOYEE_DISMISSED`) для службы HR.
  - `file-events` — уведомления о загрузке файлов администраторам.
- **REST API:**
  - `GET /api/notifications` — получение списка уведомлений с фильтром по `isRead` и пагинацией.
  - `GET /api/notifications/unread-count` — быстрое получение счетчика для бейджа колокольчика.
  - `PATCH /api/notifications/{id}/read` — отметка конкретного уведомления прочитанным.
  - `POST /api/notifications/mark-all-read` — массовая отметка всех уведомлений.

## 7. Тестирование и метрики покрытия JaCoCo

### Как JaCoCo считает покрытие?
JaCoCo работает на уровне Java-байткода через Java Agent (`org.jacoco.agent`).
1. **Line Coverage (По строкам):** Отношение исполненных строк исходного кода к общему числу строк с исполняемыми инструкциями.
2. **Instruction Coverage (По байткод-инструкциям):** Базовая и наиболее точная метрика JaCoCo. Считает количество выполненных JVM-инструкций независимо от форматирования кода.
3. **Branch Coverage (По ветвлениям):** Считает выполнение условий `if/else`, тернарных операторов и `switch`.

### Итоги покрытия проекта ЛР №4:
- Общее число тестов: **365+ автоматических тестов**.
- Все тесты выполняются за **$\approx 55$ секунд**.
- **Линейное покрытие по всему проекту: 92.3%** (при требовании ТЗ $\ge 70\%$).
- Каждый микросервис в отдельности имеет покрытие от **80.0% до 100.0%**.

## 8. Шпаргалка: частые вопросы преподавателя на защите

**Вопрос 1: Что произойдет, если брокер `kafka-2` внезапно отключится?**
> *Ответ:* Система продолжит работать без сбоев. Поскольку фактор репликации равен 3, а `min.insync.replicas=2`, оставшиеся брокеры `kafka-1` и `kafka-3` содержат полные копии всех партиций. Если `kafka-2` был лидером какой-то партиции, контроллер KRaft мгновенно выберет нового лидера из оставшихся нод в ISR. Ни одно сообщение не потеряется.

**Вопрос 2: В чем разница между топиком (Topic) и очередью (Queue)?**
> *Ответ:* В классической очереди (RabbitMQ / JMS) сообщение после прочтения консьюмером удаляется. В Kafka топик — это постоянный лог. Сообщения не удаляются при чтении, а хранятся заданное время (Retention Period). Несколько независимых Consumer Groups могут читать один и тот же топик с разной скоростью и со своими смещениями (Offsets).

**Вопрос 3: Зачем нужен `FileStoragePort` в Clean Architecture, если можно сразу внедрить класс для работы с диском?**
> *Ответ:* Это принцип Dependency Inversion. Внутренний слой Application не должен зависеть от инфраструктурных библиотек и деталей дискового ввода-вывода. Слой Application определяет контракт (`FileStoragePort`), а слой Infrastructure его реализует (`LocalDiskFileStorageAdapter`). Это позволяет без изменения логики приложения перейти на облачное S3-хранилище или сетевую файловую систему, а также легко мокировать хранилище в тестах.

**Вопрос 4: Как гарантируется, что уведомление доставлено конкретному сотруднику, а не всем?**
> *Ответ:* В сущности `Notification` есть поля `recipientUserId`, `recipientEmployeeId` и `targetRole`. Консьюмер Kafka извлекает ID адресата из события (`recipientUserId` или `employeeId`), а при запросе `GET /api/notifications` сервер фильтрует записи по ID текущего авторизованного пользователя из JWT токена и его роли.
